## Context

当前系统由一个 Node.js + Express + SQLite 的轻量后端和一个 Vue 3 前端组成，核心能力是创建单场比赛、实时计分、撤销操作和大屏比分展示。后端现有数据模型只覆盖 `teams`、`matches`、`events`，接口也只服务于当前进行中的单场比赛。

本次变更的背景是：仓库中的 `/Users/ik/Desktop/zq/brsms-demo/backend/data` 已经存在 `brsms.db` 与多份 CSV 数据文件，内容涵盖比赛、球队、球员、积分榜和比赛技术统计。系统需要在保留实时计分演示能力的前提下，新增面向“管理与查询”的成绩统计能力，让用户能够像管理图书数据一样，按不同维度浏览与检索比赛数据。

约束条件：
- 现有实时计分链路不能被破坏，`/`、`/control/:matchId`、`/scoreboard/:matchId` 仍需可用。
- 数据来源以现有 `backend/data` 为主，优先复用 `brsms.db`，CSV 作为补充或初始化来源。
- 当前后端是单文件 `index.js` 结构，新增能力时需要控制复杂度，避免一步重写整个服务。

## Goals / Non-Goals

**Goals:**
- 为比赛、球队、球员、积分榜和技术统计建立统一的数据访问入口。
- 新增管理端页面，支持比赛列表、比赛详情、球队/球员基础查询和统计展示。
- 在前后端中明确“实时计分数据”和“历史统计数据”的职责边界，避免互相干扰。
- 为后续实现 specs 与 tasks 提供稳定的技术拆分基础。

**Non-Goals:**
- 不在本次设计中引入复杂权限系统、登录鉴权或多角色后台。
- 不重构现有实时计分为全新的后端框架或 ORM 架构。
- 不在本次范围内设计复杂的数据编辑工作流，例如批量导入向导、审批流或可视化报表拖拽。
- 不保证兼容任意未知格式的外部数据文件，仅覆盖仓库内现有 SQLite/CSV 结构。

## Decisions

### 1. 以 `brsms.db` 作为主查询数据源，CSV 作为兜底或初始化来源

决策：
- 管理功能优先直接读取 `/backend/data/brsms.db` 中的数据表。
- 当某类数据尚未入库或表结构不完整时，再从对应 CSV 文件读取并做最小映射。

原因：
- SQLite 已经是当前运行时直接依赖，复用成本最低。
- 直接面向数据库查询更适合列表筛选、详情聚合与统计展示。
- 保留 CSV 兜底可以减少对现有数据资产的依赖风险。

备选方案：
- 方案 A：只读 CSV。缺点是查询、筛选、关联统计的实现复杂度更高。
- 方案 B：启动时强制把所有 CSV 全量导入数据库。缺点是需要额外的数据迁移逻辑，当前阶段成本偏高。

### 2. 在后端新增“管理查询 API”，与实时计分 API 分层

决策：
- 保留当前 `/api/matches/:id/score`、`/undo`、`/quarter` 等实时计分接口。
- 新增一组偏查询的管理接口，例如比赛列表、比赛详情、球队列表、球员列表、积分榜、技术统计查询等。

原因：
- 实时计分接口关注“写入与广播”，管理接口关注“读取与聚合”，两者职责不同。
- 分层后更容易保证已有演示链路不受影响。

备选方案：
- 直接扩展现有 `/api/matches` 一个接口承载全部查询。缺点是语义混乱，后续维护成本高。

### 3. 后端先在 `index.js` 内做模块化拆分准备，而不是立即大重构

决策：
- 第一阶段仍可保留单进程 Express 服务，但要把新增逻辑按“数据访问函数 + 路由处理函数”方式组织。
- 当功能稳定后，再考虑把查询逻辑拆到独立模块文件。

原因：
- 当前代码体量较小，先做轻量模块化即可满足需求。
- 避免为了架构整洁而在需求尚未验证前做无关重构。

备选方案：
- 一次性重构成 MVC/Service/Repository 多层结构。缺点是改动面过大，且与本次增量需求不匹配。

### 4. 前端新增独立“管理入口”，保留原有三页流程

决策：
- 保留现有 `SetupView`、`ControlView`、`ScoreboardView` 路由。
- 新增管理端路由，例如总览页、比赛列表/详情页、球队/球员页、统计页。

原因：
- 用户当前已有的演示入口简单直接，不应被管理场景打断。
- 管理页面与实时大屏页面的信息密度和交互方式差异明显，分路由更清晰。

备选方案：
- 把管理能力塞进现有首页。缺点是首页职责过重，既不利于演示，也不利于日常管理。

### 5. 前端状态管理按“实时比赛”与“统计查询”分 Store 处理

决策：
- 现有 `matchStore` 继续只服务实时比赛与 WebSocket 更新。
- 新增独立的管理类 store 或组合式查询状态，用于列表、筛选条件和详情数据缓存。

原因：
- WebSocket 驱动的状态与静态查询数据更新频率不同，混在一个 store 中容易产生耦合。

备选方案：
- 统一放入一个全局 store。缺点是状态边界模糊，后续维护成本高。

### 6. 管理端 UI 采用“列表 + 详情 + 统计卡片”的信息架构

决策：
- 比赛数据以列表页进入详情页。
- 球队、球员以基础列表和关键指标卡片展示。
- 积分榜与技术统计提供独立统计视图，支持最小筛选能力。

原因：
- 这类结构最接近“图书馆管理系统”的使用方式，便于浏览、检索和定位记录。
- 与现有 demo 的大屏式展示风格形成互补。

备选方案：
- 采用单页大看板承载全部信息。缺点是初版实现成本高，且不利于细节查看。

## Risks / Trade-offs

- [数据库表结构与 CSV 字段可能不一致] → 先在数据访问层做字段映射和容错，spec 中明确最小必需字段。
- [在单文件后端中继续扩展功能会加重维护压力] → 本次先限制在查询能力范围内扩展，并在 tasks 中加入必要的局部整理任务。
- [新增管理接口后，前后端字段命名可能与现有实时接口不一致] → 在设计和 spec 中统一返回字段命名，避免前端重复转换。
- [现有 README 声明的技术栈与实际代码不完全一致] → 以后续实现中的真实代码结构为准，并在必要时同步修正文档。
- [若直接读取大体量统计数据，列表页性能可能下降] → 初版只支持基础分页/筛选或受控结果集，不做复杂联表统计。

## Migration Plan

1. 保持现有实时计分接口与页面不变，新增管理查询接口和管理页路由。
2. 优先实现只读能力，让系统先能够稳定展示历史比赛、球队、球员和统计数据。
3. 完成后用现有演示流程回归验证，确保创建比赛、计分、大屏展示未受影响。
4. 如果管理功能的数据读取出现问题，可回退到不暴露新路由与新接口的状态，旧功能仍可独立运行。

## Open Questions

- `brsms.db` 内现有表结构与 CSV 字段的对应关系，是否已经完全覆盖管理端所需字段。
- 管理端首版是否需要提供数据编辑能力，还是严格限定为只读查询与展示。
- “类似图书馆管理系统”的界面偏好是更接近传统后台表格风格，还是在保留表格的基础上增加统计卡片与导航分区。
