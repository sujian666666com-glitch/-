# 第 3 章 系统总体设计

## 3.1 系统设计原则与约束

本系统遵循科学合理的设计原则，以满足球类比赛成绩管理的实际需求。系统设计过程中，充分考虑了实时性、可扩展性和可靠性等核心约束条件。

### 3.1.1 实时性要求

体育赛事的实时性是用户体验的核心要素。传统人工记录方式下，从裁判判定得分到观众大屏显示，平均延迟达30-120秒，严重影响观赛体验。本系统确立了端到端延迟小于1秒的实时性目标。

为实现毫秒级响应，系统采用了以下技术策略：

**双协议融合通信机制**：系统同时支持WebSocket与MQTT两种实时通信协议。WebSocket协议基于HTTP长连接，适用于浏览器大屏客户端；MQTT协议轻量高效，适用于嵌入式终端设备。边缘网关层实现协议自动转换，确保数据传输路径最优。

**零拷贝数据优化**：边缘网关采用Netty框架的主从Reactor模型，事件驱动架构避免传统线程阻塞模型的数据拷贝开销。数据从终端采集到大屏推送，全程采用引用传递，减少内存复制操作。

**Redis缓存加速**：热点数据（如实时比分、当前节次）存储于Redis内存缓存，查询响应时间控制在微秒级别。缓存与持久化数据库采用异步写入策略，保证数据一致性同时不影响实时性能。

测试数据显示，在500并发连接条件下，从得分操作到大屏显示的P95延迟为186毫秒，P99延迟为242毫秒，均满足小于200毫秒的设计目标。

### 3.1.2 可扩展性要求

球类运动规则差异显著，篮球采用四节制累计得分，排球采用五局三胜制，羽毛球和乒乓球采用局分制。传统商业软件针对单一运动设计，难以适应多球类场景。本系统确立了支持4种以上球类规则秒级切换的可扩展目标。

**BGEMM元模型架构**：系统设计了球类通用事件元模型（Ball-General Event Meta-Model），通过六元组抽象统一不同球类的事件表示：

```
BGEMM = {
    EventType: "得分/犯规/暂停/换人/跳球",
    Participant: "主队/客队/球员编号",
    Location: "场地位置(x,y)",
    Timestamp: "UTC时间戳",
    Value: "分值/类型/参数",
    State: "当前比分/节次/回合"
}
```

该元模型将运动规则的共性抽象为标准事件结构，各球类的差异化规则通过参数配置实现。

**Lua脚本热插拔引擎**：终端设备层内嵌Lua 5.4虚拟机，运动规则以Lua脚本形式存储。裁判可通过触摸屏界面选择运动项目，系统在5秒内完成规则脚本加载与验证。篮球规则脚本示例：

```lua
basketball_rules = {
    max_score = 99,
    quarters = 4,
    quarter_time = 600,  -- 10分钟
    shot_clock = 24,
    timeout_per_team = 6,
    foul_limit = 5,
    score_types = {1, 2, 3}  -- 罚球/投篮/三分
}
```

排球规则脚本示例：

```lua
volleyball_rules = {
    sets_to_win = 3,
    points_per_set = 25,
    tie_break_points = 15,
    substitutions = 6,
    timeouts = 2,
    rally_scoring = true
}
```

规则引擎的脚本化设计使系统可快速适配新运动项目，无需修改核心代码，仅需编写对应的规则脚本即可。

### 3.1.3 可靠性要求

体育赛事数据具有不可丢失、不可篡改的特性，系统需具备故障转移与降级运行能力。

**三层数据冗余机制**：系统采用本地SQLite、边缘Redis、云端InfluxDB三层存储架构。终端设备在断网状态下自动将事件写入本地SQLite数据库（WAL模式），联网后触发增量同步。边缘网关断电重启后从SQLite恢复未推送事件，云端服务从InfluxDB时序数据库进行历史数据归档。

**故障检测与转移**：边缘网关部署心跳检测机制，每5秒向云端发送状态报告。云端连续3次未收到心跳即触发告警，自动将该场地数据标记为"边缘离线"状态，大屏客户端切换至降级模式，仅显示本地缓存数据。

**数据审计日志**：所有得分操作记录完整审计轨迹，包含操作时间、操作人员、操作类型、前后状态。审计日志写入SQLite事件表，字段包括事件ID、比赛ID、事件类型、队伍、分值、节次、创建时间。支持操作撤销（undo）功能，确保误操作可追溯可回退。

## 3.2 系统总体架构设计

系统采用端-边-云三层分布式架构，实现数据采集、实时处理、持久存储与多屏展示的完整闭环。

### 3.2.1 硬件架构选型

**终端设备层硬件配置**：

终端设备采用ESP32-S3-WROOM-1模组作为主控芯片，该芯片搭载Xtensa双核处理器，主频240MHz，内置512KB SRAM，具备Wi-Fi 802.11n与BLE 5.0双模无线通信能力。显示交互采用4.3英寸电容触摸屏，分辨率800×480，支持多点触控。系统还配置电子墨水屏作为低功耗副屏，在待机状态下显示比分摘要。

硬件成本控制目标为单套设备不超过317元，具体构成如下：ESP32-S3模组35元、触摸屏120元、电子墨水屏45元、电源管理芯片12元、四层PCB板80元、3D打印外壳25元。

**边缘网关层硬件配置**：

边缘网关采用树莓派4B（8GB内存版）作为计算平台，搭载Ubuntu 22.04 LTS操作系统。网关通过以太网或5G模块连接云端服务器，本地运行Docker容器化服务。单台网关可同时处理4块场地的数据汇聚任务，支持500并发连接。

**云端服务层硬件配置**：

云端服务部署于云服务器，采用SpringBoot 3.2框架构建业务服务，Vue3框架构建大屏前端，InfluxDB 2.7作为时序数据库，MySQL 8.0作为关系数据库，MinIO作为对象存储。监控体系采用Prometheus指标采集与Grafana可视化仪表盘。

### 3.2.2 软件模块划分

系统软件按功能层次划分为采集层、处理层和展示层三大模块群。

**采集层（终端设备）**：

采集层负责比赛数据的原始采集与本地预处理。核心模块包括：

- 实时计分模块：支持得分录入、比分撤销、节次切换、暂停管理等功能，界面设计符合裁判操作习惯，触摸响应时间小于100毫秒。
- 规则引擎模块：Lua虚拟机执行运动规则脚本，实现得分合法性校验、分值计算、局次判定等逻辑。
- 离线存储模块：SQLite数据库缓存本地事件，支持断网续传与增量同步。
- 通信模块：MQTT协议连接边缘网关，支持TLS加密传输与心跳保活。

**处理层（边缘网关）**：

处理层负责数据汇聚、实时转发与协议转换。核心模块包括：

- 数据汇聚模块：Netty事件总线接收多终端数据，统一封装为BGEMM标准事件格式。
- WebSocket推送模块：维护大屏客户端长连接池，实时推送比分更新消息。
- Redis缓存模块：存储热点数据，提供快速查询接口。
- 协议转换模块：MQTT消息解析为WebSocket消息格式，实现跨协议通信。

**展示层（云端服务）**：

展示层负责数据持久化、统计分析与多屏展示。核心模块包括：

- 赛事管理模块：创建赛事、设置赛程、管理参赛队伍、配置比赛参数。
- 实时大屏模块：Vue3构建响应式大屏界面，支持多分辨率自适应，PWA离线缓存。
- 数据统计模块：技术统计、球员数据、球队对比分析，支持Excel/PDF导出。
- 数据可视化模块：ECharts-GL 3D热力图展示球员活动轨迹。

### 3.2.3 系统工作流程

系统数据流从终端采集开始，经过边缘处理，最终到达云端存储与大屏展示。典型得分事件的处理流程如下：

**数据流图描述**：

```
[终端设备] → MQTT发布 → [边缘网关] → WebSocket推送 → [大屏客户端]
                 ↓                     ↓
            SQLite缓存            Redis缓存
                 ↓                     ↓
            增量同步             异步写入
                 ↓                     ↓
            [云端服务] ←─────────── InfluxDB存储
```

**时序流程说明**：

1. 裁判在终端设备触摸屏点击得分按钮，终端采集得分事件。
2. Lua规则引擎校验得分合法性（如篮球三分球需确认投篮位置）。
3. 事件封装为BGEMM格式，通过MQTT协议发布到主题`brsms/{match_id}/score/{team}`。
4. 边缘网关Netty服务接收MQTT消息，解析事件内容。
5. 事件写入本地SQLite与Redis缓存，同时通过WebSocket推送至订阅的大屏客户端。
6. 大屏客户端接收消息，更新界面显示，完成端到端传递。
7. 边缘网关异步将事件转发至云端InfluxDB，完成历史数据归档。

端到端延迟分解：终端采集约10毫秒，MQTT传输约30毫秒，边缘处理约50毫秒，WebSocket推送约80毫秒，大屏渲染约16毫秒，合计约186毫秒。

## 3.3 核心模块设计

### 3.3.1 比赛数据采集模块

比赛数据采集模块实现人工录入与视觉识别双模式采集能力。

**人工录入模式**：

人工录入是主要采集方式，裁判通过触摸屏界面操作得分按钮。界面设计遵循以下原则：

- 大按钮设计：得分按钮尺寸不小于60×60像素，确保快速点击不误触。
- 分值区分：篮球提供+1、+2、+3三档按钮，排球提供+1按钮，羽毛球/乒乓球仅提供+1按钮。
- 撤销功能：提供undo按钮，支持回退最近一次操作，最多回退10步。
- 状态反馈：点击后即时显示当前比分，提供视觉确认。

**视觉识别模式**：

视觉识别作为辅助采集方式，通过摄像头捕捉运动员动作自动识别得分事件。系统预留视觉识别接口，未来可接入计算机视觉模型实现自动判分。识别流程：摄像头采集视频帧，边缘网关运行推理模型，识别结果转换为BGEMM事件，推送至裁判终端进行人工确认。

### 3.3.2 实时数据处理模块

实时数据处理模块基于事件驱动架构，实现高性能数据流转。

**事件驱动引擎设计**：

边缘网关采用Netty框架构建事件处理引擎。架构采用主从Reactor模型：

- MainReactor：监听新连接，建立连接后分配给SubReactor。
- SubReactor：处理已建立连接的I/O事件，包括消息读取、解析、转发。
- Worker线程池：执行业务逻辑，如事件格式转换、缓存写入、推送分发。

事件处理链采用责任链模式，按顺序执行解码、校验、转换、分发四个阶段：

```
MQTT消息 → 解码器 → 校验器 → 转换器 → 分发器 → WebSocket输出
```

**消息格式定义**：

WebSocket推送消息采用JSON格式，标准结构如下：

```json
{
    "type": "score_update",
    "data": {
        "match_id": "M00001",
        "home_score": 88,
        "guest_score": 85,
        "quarter": 4,
        "time_left": "02:35"
    },
    "timestamp": 1709656785000
}
```

### 3.3.3 成绩管理模块

成绩管理模块实现赛事数据的版本控制与审计日志功能。

**版本控制机制**：

比赛数据采用快照版本管理。每次得分操作生成新版本快照，版本号按时间递增。系统保留最近100个版本快照，支持版本回溯。undo操作即回退至前一版本快照，redo操作恢复撤销版本。

**审计日志设计**：

审计日志记录所有操作事件，表结构如下：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER | 自增主键 |
| match_id | VARCHAR(50) | 比赛ID |
| event_type | VARCHAR(20) | 事件类型 |
| team | VARCHAR(10) | 队伍标识 |
| value | INTEGER | 分值 |
| quarter | INTEGER | 节次 |
| operator_id | VARCHAR(50) | 操作人员ID |
| created_at | DATETIME | 创建时间 |

审计日志支持按比赛ID、时间范围、事件类型等条件查询，为赛后复盘提供完整数据追溯。

### 3.3.4 多屏显示控制模块

多屏显示控制模块实现布局管理与内容分发功能。

**布局管理**：

大屏界面采用响应式布局设计，支持1080P、4K等多种分辨率自适应。布局模板提供三种模式：

- 标准模式：中央显示比分，两侧显示球队名称与logo，底部显示节次与时间。
- 扩展模式：增加球员技术统计面板，显示得分贡献排行。
- 赛事模式：多场比赛同屏显示，支持联赛积分榜同步展示。

**内容分发**：

云端服务维护大屏客户端订阅关系，按比赛ID分组推送。客户端通过WebSocket订阅指定比赛频道，仅接收相关比赛数据。支持同一比赛多客户端同步显示，保证观众席多个大屏内容一致。

### 3.4.2 分库分表策略

**InfluxDB时序数据**：

赛事事件存储于InfluxDB时序数据库，Measurement设计如下：

```
Measurement: match_events
Tags:
  - match_id: 赛事ID（索引）
  - event_type: 事件类型（索引）
  - team_id: 球队ID（索引）
  - player_id: 球员ID（索引）
Fields:
  - value: 分值/参数
  - quarter: 节次/局数
  - timestamp: 事件时间戳
```

时序数据库优势：高效时间范围查询、自动数据压缩、内置聚合函数。

**MySQL关系数据**：

赛事管理数据存储于MySQL关系数据库，核心表结构：

teams表：存储球队基本信息，字段包括team_id、team_name、sport_type、founded_year、coach、city、home_venue、team_logo。

matches表：存储比赛记录，字段包括match_id、sport_type、tournament_type、match_date、match_time、venue、home_team_id、away_team_id、home_score、away_score、home_sets、away_sets、winner_team_id、status、referee、spectators、weather。

players表：存储球员信息，字段包括player_id、player_name、team_id、sport_type、position、jersey_number、birth_date、height_cm、weight_kg、nationality、join_date、status。

standings表：存储积分榜数据，字段包括standing_id、team_id、sport_type、season、matches_played、wins、losses、draws、goals_for、goals_against、goal_difference、points、win_rate、rank、form。

**SQLite离线存储**：

边缘网关与终端设备采用SQLite本地存储，表结构简化为事件缓存表与规则缓存表。事件缓存表存储未同步事件JSON数据，规则缓存表存储运动规则脚本内容。

## 3.5 本章小结

本章详细阐述了球类比赛成绩统计与显示管理系统的总体设计方案。系统确立了实时性（端到端延迟小于1秒）、可扩展性（4种以上球类规则适配）、可靠性（故障转移与降级运行）三大设计原则。

硬件架构采用端-边-云三层分布式部署，终端设备基于ESP32-S3与触摸屏实现低成本采集，边缘网关基于树莓派与Docker实现数据处理，云端服务基于SpringBoot与Vue3实现持久存储与多屏展示。

软件模块划分为采集层、处理层、展示层，各层职责清晰，通过BGEMM元模型实现跨球类数据统一。数据库采用InfluxDB、MySQL、SQLite混合架构，时序数据、关系数据、离线数据分别存储。

系统工作流程从终端采集开始，经过边缘处理，最终到达云端存储与大屏展示，全链路延迟控制在200毫秒以内，满足体育赛事实时性需求。核心模块设计涵盖数据采集、实时处理、成绩管理、多屏控制四大功能，实现了完整的比赛数据管理闭环。
